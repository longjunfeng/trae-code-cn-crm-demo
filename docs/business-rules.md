# CRM 业务规则与项目记忆

本文档保存项目的隐含规则、设计原因和兼容约束，供 Codex 在每次开发前读取。

## 角色和权限

| 角色 | 允许操作 |
|---|---|
| 管理员 | 查看、新建、编辑、停用用户，查看角色权限 |
| 销售经理 | 查看和编辑用户，不负责角色管理 |
| 只读成员 | 仅查看用户信息 |

角色权限清单必须由 `GET /api/roles` 返回，前端展示不能自行编造另一套权限。

## 用户状态

- `active` 显示为“启用”。
- `disabled` 显示为“停用”。
- 停用是软停用，保留用户历史数据和最近登录信息。
- 停用用户仍可在列表中被筛选和查看，不能被物理删除。

## 数据和筛选

- 搜索可以匹配姓名、邮箱和组织。
- 角色筛选必须使用角色的完整中文名称。
- 无匹配结果必须显示空状态，不能回退显示未过滤的用户。
- 任何权限或状态筛选都不能绕过服务端已有的业务条件。
- 演示数据全部使用 `example.test` 域名和虚构姓名。

## 表单和 API 错误

- 姓名、邮箱、角色、组织均为必填。
- 邮箱必须通过基础邮箱格式校验。
- 缺少 POST 字段返回 HTTP 400。
- 找不到用户返回 HTTP 404。
- 健康检查返回 `{ status: 'ok', service: 'crm-api' }`。
- 接口失败时前端可以切换到本地种子数据，但必须显示演示模式提示。

## 设计原因

- 使用内存种子数据是为了让培训环境无需数据库即可复现。
- 发布站点使用演示模式是为了不依赖培训机器上的 API。
- 用户停用采用软停用，是为了保留历史数据并演示状态切换。
- API、页面、测试和文档使用同一组虚构用户，便于追踪需求到验证。
