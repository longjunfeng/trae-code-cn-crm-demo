# 承重墙与风险分析

## 唯一必填输入

`spec`：Spec 文档的本地路径或可访问链接。

调用示例：`使用 risk-analyse，Spec：.trae/specs/generate-system-spec/spec.md`。
无需提供变更编号、基线、文件清单、负责人或回归清单；也不强制先运行 impact-analysis。

## 自动准备

1. 完整读取 Spec。相对路径从当前工作区解析；本地 Spec 定位最近 Git 根，链接型 Spec 使用唯一工作区；仓库归属不唯一时仅询问归属。
2. 读取相关祖先 AGENTS.md、已启用项目规则、实际存在的业务规则、架构、风险地图、同目录任务与验收清单。不得编造路径或把 Spec 的目标当已有实现。
3. 只读取得 HEAD、Git 状态及相关 diff，记录当前工作区基线。无 Git 不阻止分析，但说明基线核验限制。
4. 同会话或 Spec 明确关联的影响报告可复用，但核对其 Spec、仓库、基线和工作区状态；过时则重新分析受影响部分。没有报告时，自行从源码定位候选改动和调用链，不让用户填写一套参数。

## 工作流程

1. **找承重墙**：结合调用关系、共享数据模型、核心业务流程、配置入口和测试契约，识别修改后可能影响多个功能的区域。不要只根据文件大小或旧教学名单判定风险。
2. **逐项回答四问**：
   - 为什么必须修改？对应哪条 Spec 需求？
   - 哪些入口和模块调用它，它又依赖谁？
   - 是否可在局部适配、扩展点或新增实现中完成，而不改变公共契约？
   - 修改后应验证哪些功能、接口与兼容行为？
3. **核验重要约束**：检查状态流转、校验、错误处理、接口形状和数据范围。涉及权限、认证、隔离时查真实代码，不把 role/org 等展示字段当安全边界；证据不足标“未确认”。
4. **分级并给建议**：按影响与证据判断高/中/低风险，写明理由。可不动公共模块时优先建议局部方案；必须动时列专门审查和回归要求，不自动授权。
5. **核对责任归属**：仅使用已有明确责任记录；没有就标“未指定”，不根据 Git 作者或部门猜负责人，不将补负责人作为所有分析的必填门槛。
6. **收口**：四问缺关键证据的区域标“待补证据，不建议进入实现”；只对无法推导且影响方案的业务选择追问，其他资料缺口随报告列出。

## 输出

直接在对话输出，不自动落盘：

- Spec、仓库与当前基线；采用或更新的影响报告。
- 风险地图：区域/文件、关联需求、风险级别及原因、调用方、替代方案、必需回归、证据、责任归属。
- 每个高风险区域的四问答案。
- 推荐最小变更路径、不可破坏的行为、未知项。
- 结论：可进入评审 / 待补证据 / 建议拆分需求。不得写“已经批准实施”。

与 change-budget 交接时提供同一 Spec、仓库、基线、候选文件及操作类型、禁止项、回归要求。若状态改变，提示下游重新核对。

## 边界与失败

- 只读源码、文档和 Git 状态；不执行项目代码/测试、不修改文件、不安装依赖、不提交或切换分支、不访问生产。
- 不要求用户手填可从源码取得的调用方、文件和测试列表；不假设工具存在，使用当前可用且授权的读取/搜索能力。
- Spec 读取失败则请求有效地址；归属不明则请求指定工作区；资料不足不得以低风险代替未知。
- 用户已有改动属于基线，不能自动撤销。风险地图是评审材料，不是运行时访问控制或自动阻断机制。

## 验收

仅凭 Spec 可启动且无前置报告硬依赖；风险对应实际文件与调用证据；高风险区域四问完整或明确待补；不虚构现有能力/责任人；全程未改代码。
