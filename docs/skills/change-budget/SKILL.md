# 变更预算与范围核对

## 唯一必填输入

`spec`：Spec 文档的本地路径或可访问链接。

调用示例：`使用 change-budget，Spec：.trae/specs/generate-system-spec/spec.md`。
不要求用户填写 max_files、allowed_files、base_revision 等字段；开始前自动取得，无法取得则说明限制。

## 自动准备

1. 完整读取 Spec，提取需求、验收、非目标、允许/禁止范围及已明确的预算。相对路径基于当前工作区；本地 Spec 找最近 Git 根，链接型 Spec 使用当前唯一工作区。多仓库归属无法判断才询问。
2. 读取相关祖先 AGENTS.md、已启用规则、实际存在的变更预算/业务规则/架构/风险地图及同目录 tasks.md/checklist.md。
3. 只读读取 HEAD、`git status --porcelain=v1 -z`、工作区与暂存区 diff，保留已有修改、删除和未跟踪文件的起始清单。文件名按 NUL 分隔解析，不能按空格拆分路径。
4. 复用同会话或 Spec 明确关联的影响/风险报告，并核对 Spec 与工作区是否仍一致；没有报告就从源码完成必要的影响与风险分析，不强制要求用户另提供报告。

## 制定预算

1. 按需求推导最小候选清单，逐文件写操作类型与必要性；新文件标“拟新增”。源码、测试、文档、配置全部纳入，不能把 `docs/**` 等泛目录当完整白名单。
2. 禁止范围从项目规则和 Spec 的非目标推导；冲突时标注并停止授权判断，不擅自放宽。禁止为了凑预算删除测试、降低校验或顺手重构。
3. 文件上限优先采用适用于本次需求的项目已确定规则。Spec 不能自行放宽更严格的仓库限制；存在不一致则列冲突待决定。
4. 未确定上限时给出“建议上限=最小候选文件数”，不套用固定 8 文件、不当成批准。候选数超过既有上限时建议拆分，不自行提高上限。
5. 新增、修改、删除各按一个唯一文件计；重命名作为一次操作计一项，但旧路径/新路径都必须满足范围规则。无法确认是重命名时保守计为删除+新增。同一文件多次修改不重复计数；子模块作为一个路径并标注内部范围未核验。
6. 输出明确状态“待评审”。只有现有明确批准记录且仍适用时才标“已批准”；用户调用分析 Skill 不代表批准后续编码。

## 核对已发生的改动

- 将实际 staged、unstaged、untracked 与起始快照比较，区分用户原有改动和本次新增变化。不能仅靠 HEAD diff 把全部用户改动归因于本次任务。
- 对照候选/已批准清单、禁止区域、数量上限和变更内容，读取必要 diff；`git diff --check` 只检查空白错误，不替代内容审查。
- 初次调用且无起始快照时，仅核对“当前工作区整体是否与建议范围一致”，标明无法判断改动归属，不宣称本次任务未越界。
- 相同路径已有用户改动且无法分离时标“归属未确认”，不覆盖或回退。
- 无 Git 时输出预算建议；现状核对标“未完成”，不得以空 diff 声称通过。

## 输出

直接在对话输出，不自动写文件：

- Spec、仓库、HEAD 与起始工作区摘要。
- 白名单表：精确路径、操作类型、需求依据、必要性、风险。
- 禁止项、预算数字及来源、计数口径、批准状态。
- 回归要求与停止条件。
- 如已存在改动，给实际路径/计数、范围符合情况、原有改动与归属不明项，结论“符合 / 越界 / 未能核验”。未执行的测试不得标通过。
- 超范围处理建议：列出文件、原因、局部替代或拆分方案；取得明确范围决策后再继续，不自动回退。

## 停止条件

出现白名单外文件、禁止行为或计划将超过上限时停止并报告。达到上限仍可完成已在清单内的工作，但不能再新增预算项。工具/快照不足则输出可完成的建议与核验缺口，不编造授权或结果。

## 安全边界

只读、不编码、不运行测试/构建、不安装、不提交/推送、不 reset/checkout/stash/clean；不修改用户原有改动。此 Skill 提供分析约束，不是 Git Hook、权限控制或确定性阻断器。需要落盘或实现属于另外的明确任务。

## 验收

仅提供 Spec 即可启动；候选有依据、预算有来源且未被默认为授权；新改删和重命名计数一致；用户原有改动不计入本次归属；证据不足明确标注。
