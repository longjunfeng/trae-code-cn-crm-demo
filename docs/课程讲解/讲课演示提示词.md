# 讲课演示场景与提示词

> 本文用于在 TRAE 中演示。每个提示词先读取需求和项目现状，再限定本次改动，最后检查结果。运行前确认当前项目已打开、相关文件可访问；Figma 未能读取时先说明缺口，不凭空补设计。

## 1. 前端开发演示

### 原型与需求来源

- Figma：https://www.figma.com/design/pD4DUyLyTR1ylac4XAvnI7/Trae-Code-CN-CRM-%E7%94%A8%E6%88%B7%E7%AE%A1%E7%90%86%E5%8E%9F%E5%9E%8B?node-id=0-1&p=f&t=m6RuKdepHGKiRCAw-0
- 本地原型材料：`docs/prds/一期-prd`（使用前确认路径存在）。
- 需求：`docs/requirements.md`。
- Spec：`.trae/specs/generate-system-spec/spec.md`。

### 场景 1：从已确认原型实现 CRM 用户管理页面

**演示重点**：将设计与需求转为可运行页面，避免重复生成已有功能。

**提示词**：

```text
请根据我通过 Figma 工具选中的页面，以及 .trae/specs/generate-system-spec/spec.md，实现对应的 CRM 用户管理前端。

先读取项目规则和 web 中的现有实现，简要说明原型与当前页面的差异；已有功能复用，不重复创建。原型与 Spec 冲突或关键设计无法读取时，先指出问题。

仅实现本次选中页面涉及的布局、字段、交互和必要状态，包括加载、空数据、校验失败与请求失败。沿用项目现有 Vue 3、TypeScript、样式和接口方式，不擅自增加依赖或修改后端契约。

完成后检查本次页面和已有相关功能，列出修改文件、验证结果及未完成项。不要发布站点。
```

### 场景 2：按原型局部调整用户状态字段与标签样式

**演示重点**：只改指定字段与样式，保留搜索、表单和详情等现有行为。

**提示词**：

```text
请根据我通过 Figma 工具选中的用户状态区域，局部调整 CRM 用户列表中的状态字段和标签样式。

先读取 .trae/specs/generate-system-spec/spec.md 和 web/src/App.vue 及关联样式。若用户状态字段已存在，复用现有字段，不重复添加；按照原型调整展示文案与颜色，不能仅依靠颜色表达状态。

只修改实现该展示所必需的前端文件，不改变状态枚举、接口契约、搜索筛选、新建编辑或停用逻辑。原型没有明确颜色时，沿用项目设计令牌并说明选择。

完成后展示本次 Diff，检查启用、停用两种状态及相关页面行为，说明实际验证结果和未验证部分。
```

## 2. 文档生成演示

### 场景 1：从需求生成可评审的 Spec、任务与验收清单

**演示重点**：先对齐需求与边界，再进入编码；已有 Spec 优先增量完善。

**提示词**：

```text
/spec 请根据 docs/requirements.md 和当前项目实际实现，完善 .trae/specs/generate-system-spec 下的需求规格。

先读取已有 spec.md、tasks.md、checklist.md 和项目规则，保留已确认内容，不覆盖无关修改。补齐目标、非目标、页面状态、数据模型、API 契约、异常处理和可验证的验收条件，并让任务与验收项对应需求编号。

区分已经实现的能力与待实现需求，不能把目标写成已完成事实。任务和验收项未执行时保持未完成状态。

本轮只生成或完善文档，不修改业务代码。完成后总结新增内容、关键待确认点和建议执行顺序，待我确认再进入实现。
```


## 3. 后端开发演示

### 场景 1：按 Spec 实现缺失的 CRM API 能力

**演示重点**：以接口契约为依据，只补缺失能力，不重写现有服务。

**提示词**：

```text
请根据 .trae/specs/generate-system-spec/spec.md，实现本次需求涉及的 CRM 后端接口。

先读取项目规则、server 中的源码和已有 API 测试，列出 Spec 与现有接口的差异、拟修改文件和验证方法；已有接口优先复用，只补缺失部分。

沿用现有 Node.js、Express、TypeScript 和数据存储方式。实现必要的参数校验、正常响应及错误响应，不擅自加入数据库、认证系统、第三方服务或新依赖，不改变无关接口契约。

完成后运行与本次改动相关的现有测试，检查相关接口回归；列出修改文件、实际请求响应、测试结果和未完成项。不要自动提交或发布。
```

### 场景 2：为用户列表 API 增加或完善状态筛选

**演示重点**：增加可选查询条件，同时保持旧查询和响应兼容。

**提示词**：

```text
请根据 .trae/specs/generate-system-spec/spec.md，检查并完善用户列表 API 的状态筛选能力。

先读取 server/src/index.ts、前端调用代码和已有测试。若 status 参数已经实现，先验证并只修复实际缺口；若尚未实现，按 Spec 增加可选状态筛选。

保留原有关键词、角色和组合查询行为，以及响应字段、新建、编辑和软停用逻辑。状态取值、缺省行为及非法值处理以 Spec 为准；Spec 未说明且会影响兼容时先询问，不自行决定。

状态标签颜色属于前端展示，不向后端返回值加入颜色字段。完成后检查单条件、组合条件、非法值与旧接口回归，并提供真实执行结果。不要自动提交。
```

## 4. 自动化测试演示

### 已完成操作记录

根据讲师提供的信息，已按 `.trae/specs/generate-system-spec` 需求开展以下操作：

1. 在项目对应测试目录生成前端单元测试、前端集成测试，以及本功能 E2E 与后续回归使用的冒烟用例。
2. 生成后执行测试，并将执行结果放入 `test-results` 目录。

**现场演示应以实际测试文件和 `test-results` 中的本次报告为准。上述是已完成操作记录，不代表全部用例已通过；通过数、失败数和具体文件需从实际报告核对，不填写推测值。**

### 场景 1：按需求生成并执行前端分层测试

**演示重点**：区分单元、集成与 E2E，建立“需求—用例—执行结果”的对应关系。

**提示词**：

```text
请根据 .trae/specs/generate-system-spec 下的 spec.md、tasks.md、checklist.md，检查并完善本项目的前端自动化测试。

先读取现有测试目录、测试配置、package.json 和前端实现。已有用例复用，只补缺失覆盖，不重复生成；按当前测试框架将文件放入对应测试目录，不统一塞进 E2E 文件。尚无某层测试框架时，先说明最小配置方案及所需依赖，待确认后再引入。

覆盖三层：
1. 前端单元测试：验证独立函数、状态转换及组件内部逻辑，包含正常、边界和错误条件。
2. 前端集成测试：验证组件、状态与请求层协作，明确哪些依赖使用替身，不能将纯 mock 结果称为真实后端联调。
3. 前端 E2E：验证本功能完整用户流程，并添加稳定的核心冒烟用例，供后续回归复用；联调用例使用真实本地服务，不以演示种子回退冒充联调通过。

生成或补齐后执行测试，将本次执行结果放入 test-results，保留日志及框架支持的报告、失败截图或 trace。不要清空无关历史结果，注明本次运行时间和命令。

最后列出需求与用例对应关系、实际测试文件、执行命令、通过/失败/跳过数量、报告路径及未验证范围。测试失败如实报告，不修改断言、删除用例或降低校验来制造通过。
```

### 场景 2：展示测试结果，定位失败并最小修复

**演示重点**：从失败证据定位实现问题，形成可追溯的红→绿闭环。

**提示词**：

```text
请读取 test-results 中本次测试报告，并对照 .trae/specs/generate-system-spec/spec.md 分析失败用例。

先区分需求不清、实现缺陷、测试错误与环境问题，给出相关源码位置和失败证据，不要直接把失败归因于测试。若本次报告无法确定，先列出可用报告让我选择。

在确认根因后，仅修复必要实现或有证据的测试配置问题，保留原失败日志，不削弱断言或删除用例。若涉及公共契约、已有用户修改或超出当前范围，先停止说明。

先复跑失败用例，再执行相关测试和核心冒烟回归。将新的结果放入 test-results 的独立运行目录，列出修复前后结果、修改文件、报告路径及仍未解决的问题。不要自动提交。
```

### 场景 3：执行核心冒烟回归，检查旧功能是否被破坏

**演示重点**：新功能通过后，再核对存量用户流程。

**提示词**：

```text
请按 .trae/specs/generate-system-spec 的验收要求，执行本项目现有前端冒烟与核心 E2E 回归。

先核对实际用例、运行配置和所需本地服务；复用已有测试，不重新生成一套。优先覆盖列表加载、搜索筛选、新建校验、查看详情、编辑和启用/停用中实际存在的核心流程，并包含本次新增功能。不要加入项目未实现的登录或权限流程。

将本次结果保存到 test-results 的独立运行目录，报告命令、运行环境、通过/失败/跳过数量及产物路径。发现失败时保留证据并指出受影响业务；没有失败也只说明已执行的覆盖范围，不宣称全项目无问题。
```

## 5. 需求变更影响分析演示

### 场景 1：仅输入 Spec，识别直接与间接影响

**演示重点**：先分析调用链、修改候选和回归范围，再决定如何实现。

**提示词**：

```text
请读取 docs/skills/impact-analysis/SKILL.md 并按其中流程执行。
Spec：.trae/specs/generate-system-spec/spec.md

本轮只读分析，不修改代码或文档。请自动从 Spec 与当前仓库获取上下文，输出直接/间接影响、调用链、最小候选修改文件、替代方案和回归要求。

区分现有能力、待实现需求和证据缺口；候选文件不代表已批准修改。不要要求我重复填写可从文档与源码取得的参数。
```

## 6. 核心模块风险分析演示

### 场景 1：仅输入 Spec，识别承重墙并回答修改前四问

**演示重点**：识别高风险公共模块，说明为什么改、谁受影响、有没有替代方案、改后测什么。

**提示词**：

```text
请读取 docs/skills/risk-analyse/SKILL.md 并按其中流程执行。
Spec：.trae/specs/generate-system-spec/spec.md

本轮只读分析，不修改代码。请自动结合当前实现、风险地图及可用影响报告，识别本需求涉及的公共服务、核心接口和其他高风险区域。

对每个高风险区域回答：为什么必须修改、有哪些调用方、能否不改公共模块完成、修改后必须回归什么。给出有源码依据的最小方案和风险结论，负责人未知则标未指定，不能猜测。
```

---

**使用边界**：以上均为优化后的演示提示词，不表示本次已重新执行开发或测试。项目 `docs/skills` 中的文件只有在已导入或明确读取时才使用；不假设该目录会被 TRAE 自动发现。演示优先使用独立副本，保护原工作区已有改动。
